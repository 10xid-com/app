10XiD Login Architecture

A single sign-in at login.10xid.com so customers edit their own digital business card, and staff can reach every one of them — auditably.

Drafted 12 Sep 2026 Repo 10xid-com/login Status Awaiting go-ahead Code written None yet

The short answer

Does the idea make sense?

Yes — and it's the right thing to build next. You sell "Unlimited Updates" at $10/month but there is no way for a customer to make one. Every "can you change my phone number" is you, by hand, in Elementor, on a $10/month account. A login plus a self-serve editor converts your largest ongoing cost into the product itself.

Three parts of the brief as written don't work, and one is physically impossible rather than merely unwise. All three have a version that gives you what you actually wanted. The plumbing underneath turns out to be simpler than the brief assumed, because of one thing nobody had noticed: the public cards don't need a login at all.

This kills the obvious schema

A table with columns for phone, email, address, facebook, instagram… cannot represent these two cards. One needs nine socials and no address; the other needs an address with four map buttons and no hours. LinkedIn appears twice on one card, so even "one row per platform" breaks. The model has to be an ordered list of typed blocks.

Three things that don't work as asked

And what to do instead

Impossible

"it needs to be built in a way where cookies do not expire … and the option whether you want to stay logged in for 1 hr 2 hr"

These are opposites, and the first is unachievable in any current browser. Chrome has clamped cookie lifetime to 400 days since Chrome 104, Firefox since 103 — silently, on both Expires and Max-Age. There is no setting that makes a cookie permanent.

A never-expiring session is also the thing you least want here. A login that can read every customer's data must be killable now — and a session you cannot expire is a session you cannot revoke.

What you actually want

A session that never breaks unexpectedly, which is a different mechanism: two clocks enforced on the server. An idle clock that restarts on every visit, so an active customer is never logged out; and an absolute cap that renewal can never push past. The cookie is disposable and re-issued on each visit, so it never approaches 400 days. One checkbox — "Keep me signed in" — not a duration picker. 30 days for customers, 8 hours plus a 30-minute idle timeout for staff.

Backwards

"it needs the option for the visitor to tell if its a user (us) or a client"

A dropdown is a claim, not a fact. Whatever the visitor selects, the server still has to check who they are — so the selector adds a step, adds a way to leak which email addresses are staff, and adds a field that must never be trusted but looks like it can be.

What you actually want

One form. The server reads the role off the account record after authenticating and routes accordingly — customers to their card, staff to a card picker. You already chose this. The role is never an input, so no amount of form tampering gets a customer a staff session.

Resolved — simpler than expected

"wrap authority should capture log in cookies using login.10xid.com"

Wrap Authority's own site is wrapauthority.net — a different registrable domain from 10xid.com. No cookie can cross that boundary. That is a browser rule, not a configuration, and third-party cookie blocking killed the old workarounds.

But you confirmed they only need to edit their own 10XiD, which lives on 10xid.com. So the hard case is out of scope — and it turns out you don't need a shared cookie for the easy case either.

What you actually want

Put the login and the editor on the single host login.10xid.com, with a cookie scoped to that one host. The public cards at 10xid.com/vwt/ are anonymous pages that need no session at all. Nothing is shared, so nothing can leak. If you later want to gate a client's own domain, that's a redirect handoff — see the seam below.

The cookie decision

The single highest-leverage call in the build

The instinct is to scope the session cookie to .10xid.com so everything under the domain shares it. Don't. A cookie set on the parent domain is sent to every host under it, including hosts that don't exist yet, and the relationship is bidirectional — any subdomain can also set a cookie on the parent. Four independent reasons apply here, and no requirement needs it:

  1. WordPress sits on the apex. WordPress 7.1 + Elementor plus plugins is the highest-probability source of a cross-site-scripting bug in your whole estate, and 10xid.com receives every .10xid.com cookie by definition. Even with HttpOnly stopping theft, script on the apex can ride the session, and a compromised WordPress can set cookies on the parent to force a chosen session onto the editor.
  2. Subdomain takeover. The Astro migration will create and destroy preview hostnames routinely. One dangling DNS record hands an attacker a host that receives every session cookie with no scripting bug needed — and it counts as "same-site", so SameSite offers nothing against it.
  3. Your own image rule. House rule AD-9 serves images from img.10xid.com, backed by Backblaze. A parent-scoped cookie attaches the live session token to every image request, sending it into a third party's access logs thousands of times a day.
  4. Cache poisoning. The public cards must be cacheable and must not vary by user. A broad cookie drags a per-user value into the cache key, which is exactly how one person's authenticated page gets served to someone else.

There is also a decisive mechanical fact that forces the choice. The __Host- cookie prefix forbids a Domain attribute entirely — a __Host- cookie carrying one must be rejected by the browser. So a cross-subdomain cookie can never use it. Taking __Host- means the browser itself guarantees that no sibling subdomain and no compromised WordPress can set that cookie for your editor's host, which eliminates a whole class of attack for free.

Why Lax and not Strict

SameSite=Strict means a customer clicking a link from your own "your card is updated" email arrives logged out, and is only signed in after a reload. That is precisely the "randomly breaks" experience you're trying to eliminate. Lax is correct — and because SameSite gives no protection against a same-site compromised apex, the CSRF token and Sec-Fetch-Site check stay regardless.

One Safari trap to avoid

Safari's well-known 7-day cookie cap applies only to cookies written by JavaScript via document.cookie; a server-set HttpOnly first-party cookie can persist up to 400 days. But Safari 16.4+ does apply the 7-day cap to server-set cookies when the host looks third-party — CNAME-cloaked, or resolving away from the site's own address. This is a concrete argument against any hosted auth vendor that asks you to point a subdomain at their domain: it can silently log your Safari users out weekly.

How a customer edit reaches the live page

The question that decides whether the editor feels good

You confirmed Astro renders the cards. That leaves a real fork, and it's the one that determines whether a customer trusts the thing.

ApproachVerdictWhy
Rebuild the site on every save Rejected Build minutes aren't the problem — the allowance is ample. The problems are that the customer waits minutes to see their own phone number corrected, and that all your cards live in one repo, so every edit redeploys everyone and one bad input can break every paying card at once.
Version-keyed cache keys Rejected on inspection Looks elegant, but checking the version requires running the Worker on every request — which throws away the whole benefit of a cached page being served without invoking your code.
Render on demand, cache at the edge, purge on publish Recommended A cached card is served by Cloudflare with your Worker never running. On publish you purge that card's tag and it's live in well under a second. One customer's edit touches only their card. No build minutes consumed by content.

Corrected against live sources

Purging by cache tag used to be Enterprise-only, which historically made this design awkward on a small plan. Cloudflare opened every purge method to every plan in April 2025, including Free, and Instant Purge completes in under 150 ms. This is available to you today and it makes the recommended approach straightforwardly the best one.

The mechanism

Steady state: almost every card view is an edge hit that never runs your code. Publishing invalidates one card.

A useful consequence: because the card route is a dynamic [slug], onboarding customer number eight is a database insert, not a deployment. And 10xid.com/vwt/ keeps working with no redirect, because vwt is simply a slug in the table.

Build or buy the auth

Priced against a $10/month product

One requirement separates the options cleanly: no hosted auth vendor supports a different session length per role. Supabase, Clerk and Auth0 all configure one inactivity timeout and one maximum lifetime per project, for everybody. Your 30-day-customer / 8-hour-staff split therefore forces a session table you own — and once you own that, the library that also ships the impersonation primitives is less work, not more.

OptionVerdictDeciding factor
Better Auth (self-hosted) Recommended Free, runs on Workers, sets your own cookie on your own host. As of 1.5 (Feb 2026) Cloudflare D1 is first-class — you pass the binding directly, no adapter. Ships organizations and an impersonation primitive. Note: admin impersonation is off by default and must be enabled, and it's ESM-only since 1.4.6.
Supabase Auth Keep for the platform Already paid for and has the best exit position of any option — the password hashes come out with pg_dump. But no organizations primitive, no impersonation, and session timeouts are per-project, so it can't express the 30d/8h split.
Clerk Rejected on cost Organizations are a $100/month add-on ($85 annual). That is the revenue of ten customers, for one feature. Impersonation itself is genuinely good.
WorkOS Rejected on cost Best impersonation-with-audit story in the market — requires a typed reason, surfaces the impersonator, logs the event. But Audit Logs is the paid part: $125/month streaming plus $99/month per million events retained. The feature that justifies the vendor is the one behind the paywall.
Auth0 Rejected Its impersonation endpoint was retired years ago, so the most expensive option fails the headline requirement outright.
Lucia Gone Deprecated in March 2025. Now a learning resource with a single-file reference implementation. Don't add it as a dependency — do read its session guides.

Skip passwords entirely

Your customers are small trades businesses who will sign in a handful of times a year. One of them will forget a password and email you — which recreates exactly the support burden this project exists to remove. Resend is already wired for delivery.

So: a 6-digit code or magic link by email as the primary method for customers. No password column, no reset flow to build, no breach liability. It also sidesteps a real platform constraint — Cloudflare Workers' Web Crypto has PBKDF2 but no Argon2, scrypt or bcrypt, so anyone who reaches for the obvious npm package hits a hard build failure. Staff get the same email step plus a second factor (a passkey, or TOTP).

Worth knowing, since it's widely misreported

CPU time is not the barrier to password hashing on Workers. The Free plan gives 10 ms per request, which makes it impossible — but the Paid plan defaults to 30 seconds, raisable to 5 minutes. The real constraint is the 128 MB per-isolate memory shared across concurrent requests. You need Workers Paid for this project anyway; that's $5/month.

Staff access to every card

Without building a god mode

The tempting implementation is a flag: if (user.is_staff) skip the tenant check. Resist it. It creates two code paths — the normal one and the admin one — and the admin path is by construction the less-tested one. It also records nothing useful: your audit log says "staff signed in", not which customer's data was opened.

Do it as an explicit scope switch instead. Staff don't land on a dashboard; they land on a card picker. Choosing a card asks for a short reason, writes a time-boxed grant, and re-mints the session with that card as the active scope. Every query in the whole app is then written identically — where tenant_id = ? — for customers and staff alike. The only difference is which scopes an account may hold.

This is the same shape as AWS's AssumeRole, Stripe's account switcher, and Shopify Partners' "log in to store": you don't get ambient cross-account power, you exchange your identity for a time-boxed, single-tenant, logged credential.

  • Query uniformity — one shape, one set of bugs. For a solo developer this is the decisive argument.
  • Audit granularity — "staff acted on Vinyl Wrap Toronto, 14:02–14:31, reason: customer emailed about phone number" is the unit of disclosure you'd need if a customer ever asked what was accessed.
  • Blast radius — a stolen staff session reaches one card until the grant expires, not all of them.
  • A persistent banner — "You are acting on Vinyl Wrap Toronto as staff · Exit" — so staff never forget which card they're in. This is also how impersonation bugs get caught early.

Switching scope is a privilege change, so it rotates the session identifier — which means the security control and the audit record land on the same event.

The audit log

You don't need to buy this. An append-only table with update and delete revoked from every role, written only through a single insert function, gets you most of the way. Record the server's timestamp (never the client's), who acted, their email at the time, the active card, the reason captured at switch, the action, and a field-level before/after diff rather than a whole-row dump.

Reads are the awkward case — logging every staff read is noise. Log at the grant level instead: holding a grant for 29 minutes implies they could read everything in it.

For tamper-evidence on a trivial budget, hash-chain the rows — each stores the previous row's hash — and email yourself the day's final hash once a day through Resend. Editing history then breaks the chain, and the emailed hash is the anchor that makes the break provable rather than something an attacker can recompute. Cost: one column and one scheduled job.

Two rules that prevent most future pain

Never store a derived link. Store the phone in E.164 and the address once; generate tel:, mailto:, Google Maps, Waze, Apple Maps, MapQuest, WhatsApp, the QR code and the vCard at render time. Stored links rot the moment a customer edits their address — and Nusens has four map providers off one address.

Store the caps on the session row at creation. Otherwise a later role change retroactively lengthens a session that's already live.

Draft and publish — build it on day one

Not for workflow sophistication. Because a customer typing into a live page publishes half-finished states to the public internet — a partially-typed phone number on a card whose QR code is on the side of a truck. Editing live also makes "I broke my card" unrecoverable.

The cheap version is enough: two columns, a Publish button, a "you have unpublished changes" marker, and the last ten published snapshots for one-click restore. Retrofitting this after customers are already editing live means a migration plus a behaviour change on a live paying product.

Two things your current cards do that a rebuild would quietly lose

  • Email obfuscation. Your cards hide the address in the markup. Rendering a plain mailto: would be a regression customers notice as spam.
  • Six Elementor popups on the Vinyl Wrap Toronto card alone. Nobody has catalogued what's inside them. This is the most likely source of "the new one is missing something" after cutover — inventory them before cloning.

Moving the live cards across

Seven paying URLs that must not break

Put one Worker on 10xid.com/*. It checks the first path segment against a list of migrated slugs: a match renders from the database, anything else is proxied straight through to WordPress on a separate origin hostname and returned unchanged.

Migrating a customer then becomes a data change with instant rollback — remove the slug from the list and they're back on WordPress — rather than a Cloudflare route edit per customer. WordPress keeps serving /wp-admin and everything not yet moved.

The detail that would actually break a paying customer

The live URLs have a trailing slash: 10xid.com/vwt/. That exact form is printed on vehicles and encoded in QR codes that cannot be reprinted. It must return 200, not a 301 to the slashless variant. Set Astro's trailingSlash: 'always' and serve the slashed form canonically. Verify every URL against a captured inventory before flipping a slug — your existing "list every page" and "compare old and new addresses" procedures are exactly this.

Move the customer cards first; they're simple single pages and they're the valuable, fragile part. Keep 10xid.com's own marketing pages on WordPress until last. login.10xid.com is a separate hostname with its own Worker and doesn't interact with apex routing at all.

Non-negotiables

The list to check before this goes live

  • Session cookie is __Host- prefixed, host-scoped, HttpOnly, and never touched by JavaScript.
  • Sessions live server-side and are revocable instantly. A "your active sessions · sign out other devices" screen is the cheapest incident-response tool you will ever build.
  • Role comes off the account record after authentication, never from the form. Any requested duration is clamped server-side against the role's cap, and a request for an out-of-policy value is logged — it's cheap attack signal.
  • Session liveness is decided from the database row, never from the cookie's own expiry. A client can keep sending an expired cookie.
  • Session identifier rotates on sign-in and on every scope switch.
  • Staff require a second factor, get 8 hours absolute plus a 30-minute idle timeout, and can only reach one card at a time through a reason-carrying grant.
  • CSRF: double-submit token plus a Sec-Fetch-Site check on every state-changing request. Enable Astro's security.checkOrigin.
  • Build fails if any authenticated route is prerendered — Astro middleware does not run at request time on prerendered pages, so the auth check would silently evaporate and ship the page publicly.
  • Logo uploads are proxied through the Worker, not presigned. Backblaze's S3 API has no POST-policy support, so you cannot cap upload size at the storage layer. Proxying buys real size enforcement, magic-byte type sniffing, and one audited write path. Use content-addressed keys so a new logo is a new URL that never needs purging.
  • Backblaze credentials are a bucket-scoped restricted key, never the master key. No admin or service key is ever bound to the Worker that serves logged-in requests.
  • Login is rate-limited.
  • Put Cloudflare Access or an IP allowlist in front of wp-login.php and /wp-admin now. It costs nothing and shrinks the window while WordPress still shares the domain.

The seam you asked not to be painted into

You may later want the 10XiD sign-in to gate a client's own site on their own domain. That costs nothing to preserve today: keep "authenticate the user" and "establish a session on this host" as two separate functions, with no cookie-writing logic anywhere else. The day it matters, you add one route that redirects back to the requesting site with a single-use, short-lived, audience-scoped token which that site exchanges for its own cookie on its own domain. That's a day's work instead of a rewrite — and it's the only durable pattern, since third-party cookies aren't coming back.

Don't build it now. Just don't scatter cookie writes.
